# 원본 트랙 에셋 복구 파이프라인

## 결론

현재 설치본의 `track_<code>.rho`는 다음 원본 에셋을 실제로 포함한다.

- `track.1s`: 정방향 트랙 장면 트리와 삼각형 메시
- `track_rvs.1s`: 역방향 변형(없는 트랙도 있음)
- `skydome.1s`: 하늘/배경 메시
- `xt_minimap.png`: 인게임 미니맵 선
- `xt_bigmap.png`: 큰 맵 표시용 이미지
- `xt_trackCard.png`, `xt_trackThumb.png`: 트랙 선택 UI 이미지

별도 `collision.*` 파일은 13개 조사 대상에서 발견되지 않았다. 대신 `track.1s`
장면 트리에 `road`, `RoadObj`, `wall`, `v_wall`, `fence` 등의 원본 노드명이
들어 있다. 이 이름들은 주행면/장벽 후보를 찾는 강한 단서이지만, 원본 런타임이
어떤 태그와 속성으로 최종 충돌 대상을 선택하는지 확인하기 전에는 이름만으로
충돌 메시라고 단정하지 않는다.

## `village_C101`, `village_C102` 제거

두 코드는 복구 과정에서 한때 T 목록에 있었으나 현재는 제거했다. 데모 EXE의
평문 문자열을 다시 검사해도 `village_C101`, `village_C102` 자체는 나오지 않고,
EXE에서 직접 확인되는 관련 문자열은 `.rho`, `track.1s`, `Rh layer spec 1.0`뿐이다.

현재 중국 설치본에는 같은 코드의 `.rho`가 없으므로 이번 파이프라인으로 AABB를
재추출해 대조할 수 없다. 즉 두 항목만 manifest와 SHA-256 감사 기록 없이 남는
상태였고, 나머지 13개 트랙과 같은 근거 수준을 맞출 수 없어 목록에서 뺐다.
원본 데모 Data 디렉터리를 다시 확보하면 다른 트랙과 동일하게 manifest와
SHA-256을 남긴 뒤 복원할 수 있다.

## 안전 장치

`asset_tools/rho-safe-index`는 RHO를 `FileAccess.Read`로만 연다.

1. 열기 전 원본 크기, 수정 시각, SHA-256 기록
2. 파일 트리만 JSON으로 기록 가능
3. 선택 추출은 현재 작업공간 아래 빈 디렉터리만 허용
4. 절대 경로/`..` 탈출 차단
5. 256 MiB를 넘는 단일 엔트리 거부
6. 기존 파일 덮어쓰기 거부
7. 종료 후 원본 크기, 수정 시각, SHA-256 재검증

사용한 공개 구현은 GPL-3.0 `xpoi5010/Kartrider-File-Reader`의
`37fab6415360afa83e8034f8cedb2cc6766d2fe0` 커밋이다. 이 라이브러리의
`DotNetZip 1.16.0`에는 알려진 보안 경고가 있으므로, 도구는 ZIP 관련 API나
아카이브 저장 API를 호출하지 않고 RHO 읽기 경로만 사용한다.

## 생성물

- `analysis/track-assets/*.manifest.json`: RHO 내부 파일 목록
- `analysis/track-assets/*.extracted.json`: 추출 파일별 SHA-256 포함 목록
- `analysis/track-assets/extracted/`: 트랙별 선택 추출 결과
- `analysis/track-assets/shared/`: 테마 및 공용 텍스처/모델
- `analysis/track-assets/meshes/*.ktrk`: C 로더용 little-endian 메시
- `analysis/track-assets/meshes/*.mesh.json`: 노드/텍스처/충돌 후보 보고서

## KTRK v1

`track-mesh-exporter`는 `track.1s`의 원본 계층 변환을 정점에 적용해 다음 구조로
기록한다. 좌표계는 원본과 동일하게 X/Y가 지면, Z가 높이다.

```text
header:
  char magic[4] = "KTRK"
  uint32 version = 1
  uint32 mesh_count
  uint32 total_vertex_count
  uint32 total_triangle_count
  float bounds_min[3]
  float bounds_max[3]

mesh[mesh_count]:
  char name_utf8[96]
  char texture_utf8[96]
  uint32 flags       // bit 0 road/drive 후보, bit 1 wall/fence/bound 후보
  uint32 vertex_count
  uint32 index_count
  vertex[vertex_count] { float x,y,z,u,v }
  uint32 index[index_count]
```

Forest I01을 이 방식으로 다시 계산한 AABB는
`(13.488026, 27.247574, 1.7524452)`–`(909.879, 834.4304, 118.123055)`이며,
기존 데모 복구 상수와 부동소수점 오차 범위에서 일치한다.

## KTKZ 컨테이너

13개 KTRK를 그대로 넣으면 실행 파일이 12.6 MB가 되므로, 리소스는 다음 컨테이너로
압축해 포함한다.

```text
char   magic[4] = "KTKZ"
uint32 원본 KTRK 크기 (little-endian)
uint8  raw DEFLATE 스트림 (RFC 1951, zlib/gzip 래퍼 없음)
```

`scripts/pack_track_scenes.ps1`이 .NET `DeflateStream`으로 만들고,
`src/kart_inflate.c`의 자체 구현이 실행 시 푼다. 외부 라이브러리를 쓰지 않는
기존 방침에 맞췄다. 13개 합계 12,709,660 → 3,886,066 바이트(30.6%)이고 실행 파일은
약 4.2 MB다. 기록된 원본 크기와 실제 해제 길이가 다르면 부분 로드하지 않고 거부한다.

## 트랙 상수 산출 규칙 통일

이전에는 `src/kart_demo_data.c`의 AABB 상수가 트랙마다 다른 기준으로 들어가 있었다.
13개 중 4개만 전체 메쉬 AABB와 일치했고, `village_R01`은 road 서브셋 AABB,
나머지 8개는 어느 서브셋과도 맞지 않았다. `village_R01`의 경우 AABB 중심이 실제
메쉬 중심과 24.3 단위 어긋나 장면이 자기 벽·미니맵과 따로 놀았다.

지금은 `scripts/derive_track_constants.py`가 KTRK에서 전부 다시 뽑는다.

- **AABB**: KTRK 헤더의 전체 메쉬 정점 경계
- **출발선 X/Y**: 텍스처 이름에 `start`가 들어간 road 플래그 메쉬의 정점 중심
- **지면 Z**: 그 사각형의 평면 (13개 모두 완전 평면)
- **주행 축**: 출발선 스트라이프는 도로를 가로지르므로, 긴 변에 수직인 축

따라서 장면 배치, AABB 안전벽, 미니맵 정규화, 스폰이 모두 같은 한 출처를 쓴다.
`tests/test_track_scene_assets.c`가 13개 KTRK 헤더 경계와 트랙 표의 AABB가
일치하는지 매번 확인한다.

## 출발 방향의 한계

출발선의 위치와 축은 메쉬에서 읽히지만, **랩을 어느 쪽으로 도는지는 `track.1s`에
없다.** 현재는 `+`축을 가정하고 근거 수준을 등급으로 표시한다.

| 등급 | 트랙 | 의미 |
|---|---|---|
| `confirmed` | `forest_I01`, `village_R01` | 원작과 대조해 방향 확인 |
| `assumed dir` | 9개 | 스트라이프 종횡비 3 이상이라 축은 확실, 부호는 가정 |
| `assumed axis` | `ice_I01`(2.37), `ice_R01`(1.94), `ice_I02`(1.92) | 정사각형에 가까워 축도 추정 |

가정하는 방향은 두 축 모두 **월드 좌표계의 양의 방향**이다. 부호가 틀려도
카트가 반대로 서 있을 뿐이고, 수정은 `src/kart_demo_data.c`의 enum 한 줄이다.

출발선 후보는 `road` 플래그를 요구하지 않는다. 그 플래그는 노드 **이름**의
부분문자열 매칭이라 한글 노드명을 놓친다. `ice_I02`의 출발 바닥은
`r_스타트바닥+@s1`(텍스처 `ice_i02_start`)인데 이름이 한글이라 장식으로 분류돼
있었고, 플래그를 요구하던 이전 규칙에서는 이 트랙만 출발선이 없었다. 대신
평면성(`span_z <= 0.5`)을 검사한다. 13개 트랙의 출발 사각형은 모두 완전 평면이며,
이 완화로 나머지 12개 결과는 바뀌지 않는다.

### 이전에 `ice_I02`가 시작하자마자 꺼지던 원인

출발선이 없으면 `kart_demo_track_scene_ground_z`가 `track->minimum.z`로 폴백했다.
그러면 **장면 전체의 최저점**이 월드 z 0에 놓이므로, AABB 중심에 z 0으로 스폰된
카트 위로 모든 지오메트리가 올라가 버린다. 실제로 스폰 기둥에서 가장 가까운
삼각형은 월드 z 13.7에 있었고 전부 flags=0이라, 도로만 검사하던 지면 쿼리는
아무것도 찾지 못했다. 출발선 인식과 전체 메쉬 충돌 두 가지가 각각 이 문제를 만든다.

## 3D 시뮬레이터 연결 상태

Windows top-down과 `kart_3d`는 13개 트랙 전부의 KTRK를 실행 파일의 `RCDATA`로
포함한다. 로더는 magic/version, 개수 상한, 버퍼 길이, 정점 인덱스를
검증한 뒤 소유 메모리로 복사한다. 장면 좌표는 트랙 AABB 중심을 원점으로,
출발선 도로면 Z를 높이 0으로 옮겨 시뮬레이션 좌표계에 맞춘다.

렌더러는 카메라 주변 210 m 안에서 `road`/`RoadObj` 등의 후보 메시를 전밀도로,
나머지 장식 메시를 1/5 밀도로 그린다. 회색 그리드와 하늘색 AABB는 의도적으로
보조 표시로 유지된다. 노란 후보 삼각형의 충돌 사용 범위와 한계는 아래 절에
별도로 기록한다.

13개 설치 트랙의 `xt_minimap.png`는 Windows top-down/3D 실행 파일에 PNG
리소스로 포함되고 WIC로 디코딩된다. Track Map 패널의 카트 위치는 트랙 AABB를
미니맵의 실제 비어 있지 않은 픽셀 영역에 정규화해 표시하므로, 투명 여백까지
좌표 범위로 잘못 사용하는 단순 오버레이가 아니다.

각 트랙의 출발선 바닥 사각형은 위 규칙으로 찾는다. 시뮬레이터는 그 사각형
정점의 중심을 스폰 X/Y로 사용하고 그 면의 Z를 평면 지면 0에 맞춘다.
장면에는 카트별 그리드 슬롯 데이터가 없다. 가정하는 주행 방향은 두 경우 모두
**월드 좌표계의 양의 축**이며, 아래 X 반전과는 무관하게 월드 기준으로 직접
지정한다. 시뮬레이터의 축 기즈모가 보여주는 것과 같은 좌표계다.

- 스트라이프가 X를 따라 놓인 트랙: `+Y` 주행. Z축 180도 회전 쿼터니언
  `q=(w=0,x=0,y=0,z=1)`. 전방이 `-Y`에서 `+Y`로, 차체 오른쪽이 `+X`에서 `-X`로
  함께 바뀌므로 카메라·조향의 좌우 관계가 유지된다.
- 스트라이프가 Y를 따라 놓인 `village_I01`, `ice_R01`: `+X` 주행. 위 자세를
  Z축으로 -90도 더 돌린 `q=(w=0.70710678,z=0.70710678)`이며, 차체 오른쪽은
  `+Y`가 되어 같은 방식으로 좌우 관계가 유지된다.

원본 트랙 외형과 대조한 결과, KTRK로 내보낸 X축은 시뮬레이터 표시 좌표계에서
좌우가 반대였다. 이는 개별 트랙이 아니라 내보내기 규약의 성질이므로 13개 장면
모두 AABB 중심을 기준으로 `x_world = center_x - x_asset`으로 반전한다. 출발선
스폰 X도 같은 변환을 사용한다. 원본 미니맵 PNG 자체는 뒤집지 않으며, 시뮬레이션의 반전된
world X를 미니맵 원본 좌표로 되돌리는 `u = 0.5 - x_world / track_width`를
적용한다. PNG의 아래쪽 증가 Y축도 `v = 0.5 - y_world / track_length`로
변환한다. 카트 위치와 방향벡터는 동일한 공통 변환을 사용해 X 또는 Y 중 한쪽만
뒤집히는 표시 오류를 방지한다.

## 충돌 대상: 장면의 모든 메시

장면의 **모든 메시**가 충돌 대상이다. 용도는 이름이 아니라 **면 법선**으로 정한다.

- `|n_z| >= 0.20`: 주행면. 길이 1.0의 기존 바퀴 서스펜션 레이와 Möller–Trumbore
  교차 검사를 하고, 가장 가까운 교점과 위쪽 법선을 기존 서스펜션 계산에 넘긴다.
- `|n_z| <= 0.55`: 벽. 카트의 현재 차체 right/forward 축으로 벽 법선 방향 OBB
  지지 반경을 계산하고, 벽 평면 투영점이 삼각형 안에 들면 접촉 법선을 반환한다.
  동일 평면의 중복 삼각형 법선은 한 접촉으로 합친다.

반사·접선 속도 손실·각속도 보정은 새로 만든 힘이 아니라 이미 EXE에서 복구한
`kart_resolve_linear_collision` 경로가 처리한다.

이전에는 `road`/`wall` 플래그가 붙은 메시만 충돌했다. 그 플래그는 노드 이름의
부분문자열 매칭이라 신뢰도가 낮다. 테마 편차가 커서 desert는 `wall` 후보를
11~25개 찾지만 forest/ice/village 대부분은 0개이고, 한글 노드명은 아예 놓친다.
그 결과 바위·턱·나무 등 초록색으로 그려지던 지오메트리를 카트가 통과했다.
지금 이 플래그는 **렌더러의 와이어프레임 색 구분에만** 쓰인다.

전체 AABB 벽은 완전 이탈을 막는 외곽 안전벽으로 남는다. 평면 지면 폴백은
리소스가 없는 빌드와 합성 `flat_test` 트랙에서만 쓰인다. 이 구현은 장면의
지오메트리를 그대로 충돌에 사용한 것이며, 원본 런타임의 최종 노드 선택 태그를
발견했다는 뜻은 아니다.

### 메시 단위 경계로 비용 상쇄

`KartTrackSceneMesh`는 로드 시 정점에서 계산한 에셋 공간 AABB를 갖는다
(`kart_track_scene_compute_bounds`, KTRK 파일 포맷은 그대로다). 두 쿼리 모두
삼각형을 보기 전에 이 경계로 메시 전체를 먼저 기각한다. 손으로 만든 장면은
쿼리 전에 이 함수를 직접 불러야 한다.

덕분에 대상 삼각형이 3~5배 늘었는데도 실측 비용은 5 ms 서브스텝의 **0.8~2.5%**다
(`ice_R01` 50,046 삼각형 기준 0.056 ms). 바퀴 레이 4개와 차체 쿼리 1개를 합친 값이다.

## 텍스처: KTEX 테이블

KTRK 메시는 처음부터 `track.1s`가 머티리얼에 지정한 텍스처 이름과 정점별 UV를
싣고 있었다. 없던 것은 픽셀뿐이고, 그 픽셀은 추출된 테마 아카이브
(`analysis/track-assets/shared/theme_*/texture`, `track_common`)에 DDS와 PNG로
들어 있다.

`scripts/pack_track_textures.py`가 이 둘을 잇는다.

- 참조 목록은 KTRK에서 직접 읽는다. 이름 해석 순서는
  `scripts/map_track_textures.ps1`과 같다: `theme_<트랙 테마>` → `theme_common`
  → `track_common`.
- DDS는 DXT1/DXT3/DXT5와 비압축 레이아웃을, PNG는 팔레트/그레이/RGB/RGBA를
  자체 디코딩한다 (외부 이미지 라이브러리 없음, Python 표준 `zlib`만 사용).
- 박스 필터로 2의 거듭제곱 크기까지 축소한다(기본 상한 64x64). RGB는 알파로
  가중 평균하므로 컷아웃 가장자리에 투명 픽셀 색이 번지지 않는다.
- 저장 포맷은 텍셀당 RGB565 16비트 + 텍셀당 1비트 커버리지 마스크.
  래스터라이저가 곱셈 없이 샘플링할 수 있는 최소 형태다.
- 이름은 테마마다 겹치므로 키는 `"<테마>/<메시의 texture 필드 바이트>"`다.
  내용이 같은 이미지는 해시로 합쳐진다.

13개 트랙 전체에서 **키 411개 / 이미지 400개**, 원본 3.4 MB가 deflate 후
1.25 MB이며 `IDR_TRACK_TEXTURES` RCDATA 하나로 들어간다. 트랙별로 나누지 않는
이유는 같은 텍스처가 여러 트랙에 중복 등장하기 때문이다.

해석되지 않는 이름은 30개다. `ad_board_*` / `ad_fence_*` / `ad_start`는 인게임
광고 슬롯이라 데모 아카이브에 픽셀이 없고, `ice_01`, `ice_cave_B02`,
`ice_ob_a`, `ice_tree_01`도 어느 아카이브에도 없다. 이 메시들은 텍스처 없이
바닥/벽 색으로 칠해진다.

포맷 정의는 `include/kart_track_texture.h`, 로더는 `src/kart_track_texture.c`
(KTKZ와 같은 모양의 `KTXZ` 컨테이너, 같은 `kart_inflate` 사용).

## 알려진 데이터 품질 문제

`track-mesh-exporter`는 노드 이름을 `Encoding.UTF8.GetBytes`로 기록하는데,
원본이 CP949 한글인 노드는 상위 리더가 이미 잘못 디코딩한 뒤라 KTRK 안에서
깨진다. 예: `desert_I02`의 출발선 메쉬 `road_?潺???03@s0`. 지오메트리와 플래그는
영향받지 않지만, 이름으로 노드를 다시 찾을 때는 주의해야 한다.

## 남은 검증

1. 11개 트랙의 출발 주행 방향 부호를 원작과 대조 (위 등급표 참고)
2. `ice_I02`의 실제 출발선 주행면 식별
3. 원본 런타임에서 충돌 대상으로 채택하는 장면 태그/속성 식별
4. 미해석 텍스처 30개(광고 슬롯 7종, `ice_*` 4종)의 출처 확인
5. 텍스처 렌더러의 남은 항목: 스카이돔(`extracted/<track>/skydome.png`은 이미
   추출되어 있다), 카트 모델 텍스처, 카트/스키드/부스트를 깊이 버퍼에 함께
   그리기(현재는 GDI로 그 위에 덧그린다), 거리 LOD
6. 공간 분할 도입. 현재 충돌 쿼리는 road 삼각형 완전 탐색이고, `ice_R01`은
   road 후보가 가장 많아 초당 수백만 회 교차 검사가 발생한다

원본 런타임의 최종 충돌 노드 선택 조건을 찾기 전에는 이 경로를 “원본 트랙
충돌 쿼리의 완전 복구”라고 부르지 않는다.
